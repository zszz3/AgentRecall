# ADR 0031：统一产品后的五层文档体系与 ADR 治理规则

## 状态

已采用。

## 背景

在完成 V1 退役与 2.0 统一（[ADR 0027](0027-unified-v2-product.md)）、团队空间与 Skills 重构（[ADR 0028](0028-streamlined-team-space-and-skills.md)）、CLI 合并入主包（[ADR 0029](0029-unified-cli-in-main-package.md)）以及桌面端模块化拆分（[ADR 0030](0030-modular-desktop-architecture-and-guardrails.md)）之后，仓库文档出现了三类漂移：

1. 入口索引（`docs/README.md`、`docs/spec/README.md`）仍保留 V1/V2/独立 CLI 三分心智；
2. 重要重构方案与产品设计容易停留在临时会话草稿中，未按统一规则沉淀进 `docs/designs/` 与 `docs/adr/`；
3. 部分被新决策收窄或替代的历史 ADR 在索引中仍只标「已采用」，读者难以分辨当前生效状态。

## 决策

确立并长期维护 **五层分工、单一权威源** 的文档体系：

| 目录 | 定位与职责 | 更新时机与边界 |
| --- | --- | --- |
| `docs/v2/`（及根 `README.md`、`Install.md`） | **用户指南与操作参考**：安装、配置、界面操作、CLI 用法与排障 | 用户可见流程或命令变化时同步更新；历史 `docs/v1/` 仅作冻结参考，不再作为主入口 |
| `docs/spec/` | **当前代码契约**：对象模型、进程所有权、失败与兼容边界、源码与测试指针 | 随代码改动同 PR 更新；只写当前 checkout 真实行为，不写未来设想 |
| `docs/adr/` | **架构决策记录**：进程边界、数据归属、持久化兼容、冲突策略与跨模块架构治理 | 发生架构级取舍时新增编号（不复用），被替代的旧 ADR 保留原文并在索引及正文中互链替代编号 |
| `docs/designs/` | **专项设计蓝图**：完整现状诊断、架构图、交互设计与分阶段实施路线 | 规划阶段或重塑项目沉淀于此，必须显式标注状态（`设计草案` / `部分实施` / `已实施` / `已废弃`），不作为已实现契约 |
| `docs/project/archive/` | **历史归档**：不再维护的早期计划、交接文档与专项排查记录 | 冻结只读，保留旧链接跳转提示 |

### 设计到 ADR 的沉淀规则

1. **会话级设计蓝图必须毕业入库**：凡涉及跨模块架构重构或核心工作区重塑的设计，应以相对链接形式落盘到 `docs/designs/YYYY-MM-DD-<slug>.md` 并在 `docs/designs/README.md` 登记，禁止留存仅限本机的绝对路径。
2. **落地后的架构边界进入 ADR**：当设计中的边界、兼容策略或部署单元进入代码后，必须在 `docs/adr/` 新增或修订对应 ADR（记录状态、背景、决策、影响、替代方案与关联源码），并同步刷新 `docs/adr/README.md` 中所有受影响旧 ADR 的状态列。
3. **当前行为进入 Spec，单一事实源不重复拷贝**：详细字段与行为以 `docs/spec/` 和 TypeScript 源码为权威源；ADR 不复制大段操作手册，Spec 不堆积历史决策流水账。

## 影响

- 新贡献者与 AI Agent 可按「`README` → `spec/` 看现状 → `adr/` 看原因 → `designs/` 看完整蓝图」快速定位权威文档；
- 历史架构决策脉络清晰可追溯，避免被已下线的旧设计误导；
- 仅修改 `docs/` 的 PR 走仓库轻量检查路径，鼓励文档与 ADR 随架构演进高频保鲜。

## 考虑的替代方案

- **把全部设计文档塞进 `docs/adr/`**：会让 ADR 混入大量页面交互细节与未实施草案，稀释 ADR 作为「已定架构决策边界」的权威性；
- **不保留 `docs/designs/`，全部靠 PR 描述记录**：PR 描述分散在 GitHub 历史中，难以在本地仓库检索和持续对照阶段进度。
