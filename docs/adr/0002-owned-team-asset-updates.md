# ADR 0002：团队资产按归属更新并保留冲突

## 状态

已采用；补录当前团队资产实现，不表示功能已经发布。

## 背景

同一工作目录中同时存在个人配置和团队资源，用户也可能在 Pull 后修改团队副本。仅凭文件名或相同正文无法判断更新权限。远端发布和多个本地目录的文件写入也无法作为一个跨系统事务完成。

## 决策

- 使用受管记录、来源和内容摘要识别安装归属；仅自动更新或撤回未被本地修改的受管内容。个人同名内容不自动接管。
- 更新保留备份，写入前核对目录、团队和锁归属。冲突停止受影响操作并保留现场，其他可独立处理的项可以继续；取消不回滚已完成目录。
- 共享空间以持久本地工作副本为准，最近 Pull/Push 的远端快照只作为比较基准。两者分开保存；Pull 保留未发布修改，同一资源两侧变化时阻止发布，等待用户核对并重新保存。Push 只读取已保存副本，不再独立扫描来源目录。
- Pull 负责本地分发，Push 负责明确选择的发布。发布预览绑定内容和远端版本，版本变化时拒绝覆盖；不隐式强推或自动合并个人修改。
- 会话在加入共享空间时形成不可变本地快照，与本地目录和阅读索引一起提交；未上传与远端记录使用不同 ID 范围。上传后先留回执，再转换本地目录身份，避免本地整理失败导致重复上传。
- 显式恢复共享会话时，从本地快照创建新的原生 Agent 会话，保持共享副本和原始会话不变；工具记录作为文本上下文，子会话合入新会话历史，不恢复执行状态。原生文件提交后索引失败单独报告，避免重复创建。
- 会话分享单独形成不可变快照。Git 资源提交与会话附件上传可能部分成功，必须逐项报告远端结果。

## 影响

用户本地修改不会被日常同步悄悄覆盖，失败能定位到资源和目录。代价是需要归属记录、备份和恢复路径，且用户可能需要手动处理冲突。归属记录损坏时拒绝自动认领；推送结果不确定时先核对远端，不能把重复提交当成恢复策略。

## 考虑的替代方案

每次覆盖整个目录实现简单，但会丢失个人内容。无条件自动合并配置无法可靠判断用户意图。整轮任意失败就回滚所有目录会引入更复杂的恢复状态，且无法撤回已被其他成员读取的远端内容。
