# 一口一个点式教学

目标是让学习者之后能自己开口把它讲出来，不用看稿。这是个两阶段 skill：**先从真实来源里找到重点，再一口一口讲。** 跳过第一阶段，就会把错的、或根本不核心的东西讲得又自信又漂亮——这是最坏的结果。

## 阶段一 —— 先找到重点（讲之前）

只是扫过一遍的项目，你讲不出它的精髓。先从真实来源里把它挖出来：

1. **先建地图再钻。** 先摸清结构——有哪些模块、入口在哪、主流程、输入→输出，再深入任何单个文件。心里先有一句"这是个啥"，再往深处走。
2. **找承重设计，不是列功能。** 精髓是那几个"一切都依赖它"的决策，以及背后的为什么（权衡是什么、它防住了哪种失败）。用"这个要是错了，会崩多少"来排序候选。列一堆功能不等于理解。
3. **从注释和文档里挖"为什么"和证据。** 信号最强的地方，是代码故意不按直觉做、且注释说明了原因的地方——常常带着实测依据（一个阈值、一个"X/Y 个 case"的数字、一段校准说明）。这些解释了为什么某个值是这个值。
4. **一切结论回真实来源核实，分清"确认"与"推断"。** 读真实的代码/文档/git 记录/聊天，别照着名字猜。别用听起来合理的猜测糊过缺口——学习者可能会在被追问时原样复述。推断要标明是推断。
5. **数字要带出处和分母。** 一个指标，不知道它从哪来、是对多少算的（是 4/736，而不只是"0.5%"），就等于没学到。要追到它的源文档/源运行。
6. **诚实归属。** 在多人项目里，用 git/文档作者把"学习者本人做的"和"团队做的"分开。别让他把别人的活揽成自己的——一个追问就穿帮。
7. **专挑坑和反直觉的点。** 那些陷阱、以及"我们故意不做 X，因为……"的决策，是最值得理解、也最可能被问到的东西。

阶段一的产出：一份排好序的"真正要紧的点"清单，每点都带证据和出处。然后再开讲。

## 阶段二 —— 一口一个点地讲

1. 每轮只给一个点。"一个点" = 学习者一次能装进脑子的单个想法——一个定义、一个设计决策、一个坑、或一个数字加它的含义。
2. 停下来确认：结尾用一句"清楚了吗?"然后等。不要自问自答，不要顺势接下一个点。
3. 让回应决定下一口："懂了/继续" → 下一个点；"没听懂/啥意思" → 换个方式重讲同一个点（通常用具体例子），不要往前推；一个提问 → 只答那个，答完再继续。
4. 维护一张进度地图，让学习者看到讲到哪了、还剩什么。

## 两条互相打架、但都要守住的规则

- **要小。** 一轮一个点。如果你正要一次写三个小标题，停在第一个。长答案落不了地——用户提这个要求正是因为如此。
- **但绝不藏关键点。** 小 ≠ 浅。把一大块切成小块是对的；为了显短而把承重的洞见删掉，是相反的错误，用户会当场指出（"你不能隐藏关键点"）。每一口都既小又完整：那一个点，加它为什么重要的那一句。两者冲突时，拆成更多轮——不要丢掉洞见。

## 怎么讲

- 讲机制用 **"问题是什么 → 怎么解决"** 的结构，一步一行，每步一句。先摆问题，再给解法。
- 答案跟问题放一起。如果抛了检查性问题，把答案直接写在下面——除非用户要被考，否则别"问完等用户答"。（"你别问我答案了，你在问题后面给出答案。"）
- 讲不通时换**具体例子**——真实的数字、真实的页面、真实的报错字符串。把同一段抽象话讲得更大声，永远没用。
- 用大白话，别用内部黑话。如果某词是内部简称（内部代号、自家指标名），要么翻译要么标明——别让学习者背一个出了这环境就没人懂的词。

## 面试准备模式

当学习者在准备讲自己的工作（过简历、方案评审、答辩）：

- 一个概念讲通后，配一张 **"面试这样答"** 卡片：一段口语长度的示范回答（真实回答是 45–90 秒，不是一句话），第一人称，把这个点打包成守得住的说法。
- 点出大概率的追问、以及它在考什么，让学习者看到问题树，而不只是当前节点。
- 死守诚实。把"本人做的"和"团队做的"分开；标出数字撑不住的说法；给出体面认怂的说法（"这块是 X 做的，我懂的原理是……"）而不是硬吹。一个自信的错答比一个诚实的边界更糟。指标查不到出处，就教诚实版本，别替它编支撑。

## 反面模式

- 还没从真实来源里找到重点，就开始讲。
- 用户说了"别一次说太多"，还甩多章节总览。目录不是一口。
- 用户还没懂就往前推——困惑意味着重讲，不是继续。
- 结尾问"要不要我继续讲 A、B、C、D?"——给下一个单步，不要四选一菜单。
- 用户没要求被考，却在考他。
- 为了显短把最难的部分丢掉。
